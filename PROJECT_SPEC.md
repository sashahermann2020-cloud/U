# U: единая спецификация разработки

Дата: 20 октября 2026 года. Версия: 1.

## Назначение и статус

U: предметное назначение не определено в доступном репозитории. Эта спецификация задаёт обязательный каркас разработки, текстов и дизайна; продуктовые сущности и обещания не выдумываются.

Реализация интерфейса в этом репозитории не обнаружена. Ниже зафиксированы исходные требования для разработки; они не выдаются за работающий продукт.

## Как применять спецификацию

- Этот файл — обязательная точка входа для разработки; [паспорта всех маршрутов и экранов](docs/ROUTES_SPEC.md) дополняют общий контракт.
- [Реестр маршрутов](docs/ROUTE_REGISTRY.json) содержит отдельную запись для каждого URL/состояния, назначение, источник и критерии приёмки. Внутренние состояния не выдаются за независимые веб-URL.
- [Числовой визуальный справочник](docs/VISUAL_REFERENCE.json) сохраняет значения, селекторы, media-условия и последовательность деклараций. Для существующего интерфейса он описывает исходный CSS; вычисленный стиль и inline overrides проверяются в браузере.
- Подтверждённая задача пользователя уточняет требования. При расхождении кода и нормативного поведения расхождение явно исправляется или документируется в том же изменении; запрещено молча принимать устаревшую заметку за эталон.
- Бизнес-источники и даты проверки меняются только после проверки факта. Конфигурация, реализация и работоспособность внешнего сервиса — разные статусы.

## Логика и правила

Пока нет подтверждённой предметной модели, активные продуктовые URL и операции отсутствуют. До добавления первой функции в реестр вносятся: назначение, пользователь, вход, действие, результат, ветвления, ошибки, данные и права.

Для будущего CRUD: ввод → валидация → сохранение → подтверждение; ошибка не теряет ввод; удаление/замена требуют явного действия и объясняют последствия. Этот контракт применяется только к фактически добавленным операциям и не объявляет наличие CRUD в продукте.

Состояния каждого будущего экрана: initial, loading (если есть async), success, empty, invalid, error, denied (если есть права). Не показывать успех до завершения операции. Повторный запрос защищается блокировкой или идемпотентностью. Переход назад сохраняет применимый ввод; изменение исходных условий пересчитывает зависимый результат.

Первое продуктовое дополнение обязано определить модель и обновить этот документ одновременно с кодом. Текущий реестр честно фиксирует отсутствие опубликованных маршрутов.


## Маршруты и состояния

Всего записей в реестре: 0. Активных продуктовых маршрутов нет; реестр пуст намеренно, до определения предметной области.

## Подключения и данные

| Подключение | Контракт и граница |
|---|---|
| API / база / авторизация / аналитика | Не выбраны и не реализованы; подключёнными не считать |
| Будущая интеграция | До использования описать вход/выход, серверную проверку, владельца ключа, таймаут, квоту, fallback и данные |
| Секреты | Только server environment, имена без значений в документации; не помещать в клиент и Git |
| Хранение | Схема, миграция, удаление/экспорт и восстановление обязательны до сохранения пользовательских данных |

Для каждого нового подключения до реализации фиксируются: назначение, запрос/ответ, серверная валидация, авторизация, имена переменных без значений, лимит/таймаут, повторы, обработка ошибок, fallback, атрибуция, хранение и удаление данных. Неизвестный ответ провайдера не превращается в успешный результат. Статусы: «планируется», «реализовано», «настроено», «проверено»; последний требует даты и конкретного протокола.

## Визуальная система

Это начальная норма для будущей реализации, а не описание существующего интерфейса.

Системный sans-serif: system-ui, -apple-system, "Segoe UI", Arial, sans-serif. База16px/1.5; H1 32px/1.15/700, H2 24px/1.25/700, H3 20px/1.3/600, подписи14px/1.4. Палитра: фон#F8FAFC, поверхность#FFFFFF, основной текст#172033, вторичный#475569, граница#CBD5E1, действие#1D4ED8, ошибка#B91C1C, успех#166534. Цвет сопровождается текстом состояния.

Модуль4px, интервалы4/8/12/16/24/32/48/64px. Контейнер1120px, центрирован; поля24px desktop,16px mobile; текст и поля слева, action content по центру. Контрольная точка768px: сложная сетка становится одной колонкой, форма сохраняет порядок чтения. Кнопки/поля min-height48px; radius8px; border1px. Focus3px#1D4ED8, offset3px. Чтение <=70ch, длина значения не ломает страницу. Reduced-motion выключает необязательное движение. Это технический стартовый стиль; новые брендовые правила вводятся изменением спецификации, не случайным локальным CSS.


Для новых компонентов использовать существующий семантический токен и ближайший утверждённый компонент. Новое исключение по размеру, цвету, шрифту или выравниванию добавляется в этот документ и справочник. Не вводить новую локальную палитру для одной страницы. При переносе сетки на мобильный сохранять порядок чтения и доступность основного действия.

## Состояния интерфейса и доступность

- У применимых компонентов фиксируются обычное, hover, focus-visible, selected, disabled, loading, invalid, empty, success и error состояния. Отсутствующий async не требует фиктивной загрузки.
- Ошибка сообщает причину и следующее действие; введённые данные сохраняются, если это допустимо. Success появляется после завершённого действия.
- Выбор обозначается текстом и доступным состоянием (aria-current/pressed/checked), цвет не является единственным сигналом.
- Поля имеют label, ошибки связаны с полем; async-результат объявляется через доступное status/live-сообщение.
- Диалог закрывается предусмотренным действием/Escape, удерживает фокус и возвращает его в исходный элемент. Только фактически модальные элементы блокируют фон.
- Ссылки и кнопки доступны с клавиатуры; фокус не скрывается. Проверять контраст и увеличение текста, длинные строки, reduced-motion и отсутствие горизонтальной прокрутки всей страницы.

## Тексты и термины

Краткий заголовок задачи, CTA с глаголом, понятная ошибка с действием. Одинаковая сущность везде называется одним словом. Не обещать функцию, которой нет. Даты и числа форматировать по локали; сообщения не содержат внутренних технических деталей или секретов.

Единая структура сообщения: что произошло → что нужно сделать → какой результат ожидать. Не дублировать одно действие разными словами. Числа, даты, валюты и единицы форматируются согласованно с локалью. Внешний переход обозначает переход, сохранение — фактическую запись, отправка — подтверждённый приём. Технические подробности остаются в документации, если не помогают пользователю принять решение.

## Приёмка и сопровождение

Проверка текущего документа: все разделы заполнены, отсутствие продукта явно обозначено. Для будущей реализации — ветвления/ошибки/права,320/390/768/1440px, клавиатура, фокус, контраст и сохранность данных. Не отмечать будущие проверки пройденными.

Каждое изменение сопровождается записью: затронутый URL/экран, изменённое правило, проверенные входные профили, ожидаемый и фактический результат, визуальные ширины/темы/локали, ограничения проверки. Проверка только документации подтверждает корректность структуры и ссылок, но не работоспособность интерфейса или production.

В том же commit обновлять:
1. этот документ и применимые профильные правила;
2. строку ROUTE_REGISTRY и таблицу ROUTES_SPEC при изменении маршрута/экрана;
3. значения и условия VISUAL_REFERENCE при изменении визуала;
4. профильный тест или протокол ручной проверки при изменении поведения.
